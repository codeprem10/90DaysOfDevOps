# Day 04 – Linux Practice: Processes and Services

## Objective

Today I practiced Linux processes, systemd services, logs, and a basic troubleshooting flow using a real Ubuntu server.

The main goal was to build familiarity with commands that are useful when troubleshooting Linux systems.

---

## 1. Process Checks

### `ps`

```bash
ps
```

Shows processes associated with the current terminal/session.

Important columns include:

- `PID` – Process ID
- `TTY` – Terminal associated with the process
- `TIME` – CPU time used
- `CMD` – Command/process name

### `ps aux`

```bash
ps aux
```

Shows a more complete list of running processes and useful information such as CPU and memory usage.

### `top`

```bash
top
```

Displays running processes dynamically and helps monitor CPU, memory, and process activity in real time.

### `htop`

```bash
htop
```

An interactive process viewer that makes it easier to inspect and manage running processes.

### `pgrep -a sshd`

```bash
pgrep -a sshd
```

Output included:

```text
635 sshd: /usr/sbin/sshd ... [listener]
3947 sshd-session: ubuntu [priv]
4068 sshd-session: ubuntu@pts/0
```

This showed that the SSH daemon was running and that there were SSH session processes.

The main SSH process had PID `635`.

---

## 2. Service Checks

For this exercise, I selected the `ssh` service.

### `systemctl list-units --type=service`

```bash
systemctl list-units --type=service
```

This displayed the currently loaded systemd services.

The important SSH entry was:

```text
ssh.service  loaded active running  OpenBSD Secure Shell server
```

This showed that the SSH service was loaded and currently running.

### `systemctl status ssh`

```bash
systemctl status ssh
```

Important information from the output:

```text
Active: active (running)
Main PID: 635 (sshd)
```

This confirmed that:

- SSH was active and running.
- The main SSH process had PID `635`.
- The service had been running for several hours.
- systemd was managing the SSH service.

---

## 3. Log Checks

### `journalctl -u ssh`

```bash
journalctl -u ssh
```

This displayed logs generated by the SSH service.

Some useful events observed were:

```text
Server listening on 0.0.0.0 port 22.
Server listening on :: port 22.
Accepted publickey for ubuntu
session opened for user ubuntu
Connection closed
Invalid user
```

The logs showed both successful SSH activity and unsuccessful/invalid connection attempts.

### `journalctl -u ssh -n 20`

```bash
journalctl -u ssh -n 20
```

This displayed only the latest 20 SSH log entries.

Using `-n` is useful during troubleshooting because it avoids having to inspect a large amount of historical log data.

---

## 4. Network Check

### `ss -tnlp | grep :22`

```bash
ss -tnlp | grep :22
```

Output:

```text
LISTEN 0      4096         0.0.0.0:22        0.0.0.0:*
LISTEN 0      4096            [::]:22           [::]:*
```

This confirmed that TCP port `22` was listening on both IPv4 and IPv6 addresses.

## 5. Mini Troubleshooting Flow

If someone reports that SSH is not working, I can investigate it step by step instead of immediately restarting the service.

### Step 1 – Check the process

```bash
pgrep -a sshd
```

Question:

> Is the SSH process running?

### Step 2 – Check the service

```bash
systemctl status ssh
```

Question:

> Is the SSH systemd service active and running?

### Step 3 – Check recent logs

```bash
journalctl -u ssh -n 20
```

Question:

> What has been happening with the SSH service?

### Step 4 – Check the network port

```bash
ss -tnlp | grep :22
```

Question:

> Is SSH actually listening on port 22?

### My server's result

```text
Process  → SSH process is running
Service  → ssh.service is active
Logs     → SSH is receiving connections
Port 22  → Port is listening
```

If all four checks are healthy but SSH is still inaccessible, I would investigate other layers such as firewall rules, AWS Security Groups, networking, or client-side SSH configuration.

## 6. Key Learnings

### Process vs Service vs Logs

A process is a running instance of a program.

A service is a system-managed application/background component, commonly managed by systemd on modern Linux systems.

Logs record events and messages generated by services and the system.

For SSH:

```text
systemd
   ↓
ssh.service
   ↓
sshd process
   ↓
PID 635
   ↓
TCP port 22
```

Useful commands:

| Question | Command |
|---|---|
| What processes are running? | `ps`, `ps aux`, `top`, `htop` |
| Is SSH process running? | `pgrep -a sshd` |
| What services are running? | `systemctl list-units --type=service` |
| Is SSH service running? | `systemctl status ssh` |
| What happened? | `journalctl -u ssh` |
| What happened recently? | `journalctl -u ssh -n 20` |
| Is port 22 listening? | `ss -tnlp \| grep :22` |

## 7. Why This Matters for DevOps

In production, problems often need to be investigated quickly.

Instead of randomly restarting services, I can follow a structured approach:

```text
Process
   ↓
Service
   ↓
Logs
   ↓
Network
```

This practice helped me build basic Linux troubleshooting muscle memory.

The commands I practiced today will be useful when diagnosing problems with SSH, web servers, databases, Docker, and other Linux services.
